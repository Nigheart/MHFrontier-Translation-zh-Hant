# MHF 离线版「任务列表乱码」排查报告

日期：2026-11-14　范围：只读分析，未修改任何游戏文件
脚本与中间产物：`工作区\`（`_q*.py` / `_q*.txt`）

---

## 一、结论先行

**乱码不是 `mhf.bin` / `mhf_90c.bin` / `result.bin` / `mhfdat.bin` 造成的，也不在 `dat\` 下任何文件里。**

游戏内「任务列表 / 任务名」的数据来自 **`Erupe\bin\questlists\list_*.bin`**（服务端原样下发的客户端二进制），任务详情文本来自 **`Erupe\bin\quests\*.bin`**（54,963 个，JKR+LZ 压缩）。

乱码的根因是：**这些 list 文件被汉化工具改写后，字符串长度与结构槽位不一致，且把 NUL / 空格填充写进了 `≪...≫` 字符串内部**，导致客户端按 C 字符串（NUL 结尾）读取时**在串中间被截断并错位**，后续字节被按半个双字节字符解码 → 出现「半角片假名（看起来像拉丁字母/符号）＋ 生僻汉字/方块」的混合乱码。

用户描述的 `1♠C &CC@VCC UCC灬CC 6CC` 与实测的错位解码结果同源：

- `♠` 来自 cp932 的 `0x81 0x9A`（真实字形是 **`★`**，就在 `≪Ｇ★７…≫` 里）
- `灬` 是 cp932 的 **IBM 扩展区字符 `0xFA 0x40`**，正常日文任务名不可能出现，只有"字节被错位拆开"才会得到
- 大量 `C`（0x43）来自 `94 43`（`任`）等双字节字符的第二字节被当成单字节 ASCII

### 编码

任务文本一律 **cp932（Shift-JIS）**，NUL 结尾。
汉化采用"用日文字符集里的汉字拼中文"（如 `≪獵人的基本≫`、`已納品所有委托物品`），字节层面仍是 cp932。

### quests/*.bin 解压方法（可复用现有工具）

```python
import struct
from lz_decode import jpk_lz_decode
b = open(r'...\bin\quests\00001d0.bin','rb').read()   # JKR\x1a, type=3
usize = struct.unpack_from('<I', b, 12)[0]
data  = jpk_lz_decode(b[struct.unpack_from('<I', b, 8)[0]:], usize)  # 12256 字节
```

00001d0 解压后字段（0x2E80 处 8 个指针）实测全部正确：

## 三、乱码机理与直接证据

### 3.1 证据 A：`≪Ｇ★７ 活動任務≫` 比原文多 1 个字节

`list_0.bin`

| | 偏移 | 字节数 | 内容 |
|---|---|---|---|
| 原版（`Backups\list_0.bin`） | 0x0440 | **18** | `81 E1 82 66 81 9A 82 56 83 43 83 78 83 93 83 67 81 E2` = `≪Ｇ★７イベント≫` |
| 当前（汉化） | 0x0438 | **19** | `81 E1 82 66 81 9A 82 56 20 8A 88 93 AE 94 43 96 B1 81 E2` = `≪Ｇ★７ 活動任務≫` |

汉化在 `Ｇ★７` 与 `活動任務` 之间**多插了一个 0x20 空格**，使任务名溢出 1 字节。
从错位位置开始按 cp932 解码，实测得到：

```
从 0x043D（-3）: 痰f★７ 活動任務≫   ␊嘉特蕾亞的推薦
从 0x043F（-1）: f★７ 活動任務≫   ␊嘉特蕾亞的推薦
从 0x0441（+1）: 嘯V 活動任務≫   ␊嘉特蕾亞的推薦     ← 出现「嘯V」，与乱码中的 V/C 同源
```

### 3.2 证据 B：字符串中间被塞入 NUL / 空格（最致命）

**`list_126.bin` 0x31F8 与 0x382C** 两处，任务名被写成：

```
81 E1 90 E2 93 87 (≪絶島)
00 00 00 ... (53 个 0x00)
92 6E 92 EA 81 E2 (地底≫)          共 69 字节，而原文槽只有 22 字节
```

`list_0.bin` 里则是用空格/换行填充：
- 0x7513 `≪      \n司銀龍≫`（17B，原 `≪司銀龍≫` 10B）
- 0x755A `≪辿        \n異種≫`（19B，原 10B）
- 0x6277 `≪Ｇ★６ 活動任務≫`（19B，原 18B）

**C 字符串读到第一个 `0x00` 就结束**，客户端只会显示 `≪絶島`，剩下的 `地底≫` 与后继字段全部前移/错位；再往后每一段都从"半个 cp932 双字节字符"开始读，于是出现：

- 半角片假名（cp932 `0xA1–0xDF`）→ 看起来像拉丁字母/符号
- 生僻汉字 / IBM 扩展区字符（如 `灬` = `0xFA 0x40`）→ 字体无字形 → 红色方块

**这与用户描述的"红色方块字 + 拉丁符号混杂"完全一致。**

### 3.3 证据 C：几乎全部任务名长度都被改写

对比 `list_0.bin` 与 `Backups\list_0.bin`，63 个 `≪…≫` 任务名中：

```
[0]  cur=12B '≪活動任務≫'        old=20B '≪イベントクエスト≫'
[1]  cur=19B '≪Ｇ★７ 活動任務≫'  old=18B '≪Ｇ★７イベント≫'        ← 溢出 +1
[2]  cur=12B '≪極限挑戰≫'        old=18B '≪超難関クエスト≫'
[10] cur=22B '≪Ｇ★１ Event Quest≫' old=18B '≪Ｇ★１イベント≫'
[57] cur=17B '≪      \n司銀龍≫'   old=10B '≪司銀龍≫'               ← 空格填充
```

`list_42.bin` 里同一任务名被拆成两段塞进 20 字节：
`≪高級門            \n票≫`、`≪            \n高級門票≫`。

`list_126.bin` 更严重（88 个标题对 60 个旧标题，条目数都变了）。

> 完整坏槽清单见 `_qi_bad.txt`（逐文件、逐偏移、含 hex）。

## 四、修复方案

### 4.1 先回滚验证（最稳）

`Backups\` 里可用的是：

| 文件 | 当前 | 备份 | 能否直接回滚 |
|---|---|---|---|
| list_0.bin | 36,250 | 35,515 | ✅ 可以 |
| list_42.bin | 34,897 | 34,496 | ✅ 可以 |
| list_84.bin | 36,532 | 36,200 | ✅ 可以 |
| list_126.bin | 36,202 | 35,515 | ✅ 可以 |
| list_168.bin | 36,221 | 13,982 | ❌ 备份是 2020 年老版，会丢任务 |
| list_210.bin | 23,564 | 无 | ❌ 无备份 |

先把能回滚的 4 个复制到别处做对照（**不要直接覆盖游戏文件**），用其中一份替换测试，重启 Erupe 看任务列表是否恢复日文。

```powershell
# 备份当前汉化版到工作区，再回滚
Copy-Item '<游戏目录>\mhzz\MHFCN\Erupe\bin\questlists\list_0.bin' '工作区\list_0.han.bak'
Copy-Item '<游戏目录>\mhzz\MHFCN\Erupe\bin\questlists\Backups\list_0.bin' '<游戏目录>\mhzz\MHFCN\Erupe\bin\questlists\list_0.bin'
```

若回滚后正常 → 确认是汉化文件问题；若仍乱 → 问题在服务端/客户端编码（见 4.4）。

### 4.2 正确的汉化写法：等长替换、NUL 只补在串尾

对 `list_*.bin` 的每个任务名字段：

1. 原槽字节数 = 原字符串字节数（cp932，含结尾 `0x00`）
2. 新字符串 cp932 编码后 **必须 ≤ 原字节数 - 1**
3. 不足部分**在结尾 NUL 之后**用 `0x00` 补满，**绝不允许**：
   - 在 `≪…≫` 内部插入 `0x00`
   - 用空格 `0x20` 或换行 `0x0A` 填充
   - 让新串长度超过原槽
4. `≪Ｇ★７イベント≫` 这类要译成 `≪Ｇ★７活動任務≫`（**不要空格**），刚好 18 字节 = 原长度

### 4.3 校验脚本（找到所有坏槽）

```python
# 检查 list_*.bin 里每个 ≪...≫ 任务名是否含内部 NUL / 是否等长
import pathlib, re
BASE = pathlib.Path(r'<游戏目录>\mhzz\MHFCN\Erupe\bin\questlists')
for f in BASE.glob('list_*.bin'):
    b = f.read_bytes()
    for m in re.finditer(b'\x81\xe1', b):
        j = m.start(); k = b.find(b'\x81\xe2', j+2)
        if k < 0: continue
        raw = b[j:k+2]
        if b'\x00' in raw:
            print(f.name, hex(j), 'INTERNAL NUL', raw[:60])
```

### 4.4 如果回滚后仍乱码：查服务端/客户端编码

- 确认 `erupe-ce.exe` 发送字符串用的是 cp932 而不是 UTF-8/UTF-16；
- 确认没有替换过 `mhfo.dll` / `mhf.exe` 的编码表；
- 用 `config.json` 的 `LogOutboundMessages` 抓包，看任务名在包里是 `81 E1…` 还是 `E2 80…`。
